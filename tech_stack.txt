1. Design Constraint — Zero Cost, No Deployment

This project is built entirely on free and self-hosted tools. No paid API, paid hosting tier, or paid database plan is used at any point. In addition, the project does not need to be deployed to a public server — it runs fully on local infrastructure (localhost + local Docker containers + a locally-run AI model). This removes an entire category of "free tier" problems (cold starts, rate limits, 90-day trial expiry, sleep-on-idle) since nothing depends on a third-party server staying up or staying within a quota.

3. Why This Architecture (Recap of Key Reasoning)

All three databases run locally via Docker — no cloud tier limits, no internet dependency for the data layer, identical behavior to a cloud deployment if one is ever needed later.

Ollama chosen over cloud LLM APIs (Gemini/Groq) once deployment was ruled unnecessary — removes the last remaining internet dependency and matches proven prior experience (VSS·RAG).

Qwen2.5 7B chosen specifically for structured-output reliability, since most of RIP's AI features (ATS breakdown, keyword extraction, project enhancement) require consistent JSON, not conversational quality.

Embeddings kept on the same local Ollama runtime as the chat model rather than split across a cloud provider — one dependency to manage instead of two, and it preserves the fully-offline goal end to end.

4. End-to-End System Workflow

Updated version of the original workflow, mapped to the actual tools chosen:

Step 1 — User registers/logs in (Express + JWT + bcrypt, user record in PostgreSQL).

Step 2 — User uploads an existing resume or builds a new one (Multer handles upload; pdf-parse/mammoth extract text).

Step 3 — Extracted resume data is structured and stored: structured fields → PostgreSQL, full document/version → MongoDB.

Step 4 — Resume content is chunked (per project/experience entry) and embedded via Ollama's nomic-embed-text, stored in Qdrant with metadata.

Step 5 — ATS Score is generated: resume text sent to the local Qwen2.5 model with a strict JSON-output prompt → score + breakdown saved to MongoDB (ats_reports) with a summary row in PostgreSQL (ats_reports_summary).

Step 6 — User uploads a Job Description — parsed, keyword-extracted, and stored in MongoDB (job_descriptions); JD chunks embedded and stored in Qdrant.

Step 7 — Resume Success Simulator queries Qdrant for semantic similarity between resume chunks and JD chunks, combines this with keyword/ATS signals, and asks the local model to produce the match score + rejection risks (simulation_reports in MongoDB).

Step 8 — Project Impact Enhancer sends a project's base description + target role to the local model, which returns a role-tailored description (project_enhancements in MongoDB).

Step 9 — User reviews AI suggestions and applies changes to their resume through the builder UI.

Step 10 — Final resume is generated and exported to PDF (pdf-lib/Puppeteer), with the updated version saved back to MongoDB's version_history.

6.2 What actually needs a decision (not just a swap)

The AI layer is the one exception. Ollama running Qwen2.5 7B needs real RAM/CPU to serve requests — free hosting tiers (Render/Railway free plans) do not have the resources to run a 7B local model. Two real options at that point:

Switch the AI layer back to cloud APIs (Gemini and/or Groq, both free-tier) for the deployed version — same prompt contract already designed, just a different provider behind it.

Keep Ollama, but run it on a small paid GPU/CPU cloud instance — only worth it if staying fully self-hosted matters more than staying free at that stage.

Recommended default if this is ever needed: cloud APIs for the deployed version, Ollama for local development — the same "provider-agnostic" prompt contract designed for the Gemini/Groq fallback earlier makes this an easy switch, since the code was never written to assume Ollama specifically.

6.3 Why this wasn't built as a design requirement now

Adding deployment concerns (environment-based config switching, secrets management for multiple environments, CI/CD) now would add complexity with no payoff for a project that only needs to run for local development and a live viva/demo. This section exists so the reasoning and migration path are on record, not because deployment is planned for this project cycle.

7. Key Decisions Log (Tech Stack)

Chose to skip deployment entirely — the project only needs to run for local development and live demo/viva, so cloud hosting adds complexity with no real benefit at this stage.

Moved all three databases from cloud free tiers to local Docker containers once deployment was ruled out — removes cold-start and rate-limit risk during a live demo.

Switched the AI layer from cloud APIs (Gemini/Groq) to fully local Ollama once "no deployment needed" was confirmed — the last reason to depend on the internet went away.

Picked Qwen2.5 7B Instruct over Llama 3.1 8B and Mistral 7B specifically for its stronger structured/JSON output reliability, which matters more here than general chat quality.

Kept embeddings on the same Ollama runtime as the chat model (nomic-embed-text) instead of a cloud embedding API, to preserve a genuinely dependency-free, fully offline system end to end.
